Four things the first CI run found, none of which could have been seen before there was one.

The English-only guard grepped every file for `§` except its own workflow, so it failed on `tests/unit/test_cli_output_hygiene.py` — the test whose job is to enforce that same rule on CLI output.

The CodSpeed job ran `pytest --codspeed`, which collects only what uses the `benchmark` fixture. Nothing did, so the job had been exiting 5 having measured nothing. The micro-benchmarks the development docs promise — adapter `apply`, `.rbs` loading, normalisation, top-k — are now written, and `mode: simulation` is passed because CodSpeed v5 requires it.

Every action was pinned to a Node 20 runtime GitHub is removing.

And the lowest-direct job, which exists to catch exactly this, was reporting three wrong floors at once — it just died in the install before it could say so. `scipy>=1.11` resolved to 1.11.1, which has no cp312 wheel against a `requires-python = ">=3.12"` package, so the job ended in a meson source build; the floor is 1.11.2. `typer>=0.12` was wrong three times over: 0.12 cannot convert a `Path | None` annotation, everything through 0.15.2 calls click's `Parameter.make_metavar()` without the `ctx` argument click now requires, and 0.15.4 caps `click<8.2`, where `CliRunner` still merges stderr into stdout — so the separation `--json` depends on could not even be asserted. The floor is 0.16. Nothing was wrong with chromadb 0.5.5 itself: it reads `model_fields` off a pydantic instance, which pydantic 2.11 deprecated, and the floor job is the only place that pairs the oldest chromadb with the newest pydantic. That warning is ignored the way torch's and transformers' already are, rather than withdrawing the 0.5.5 support the README claims over a deprecation in someone else's code.
