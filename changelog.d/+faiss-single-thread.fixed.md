The FAISS backend runs its search with OpenMP pinned to one thread. It costs nothing — FAISS parallelises across the rows of a query batch and this backend searches one vector at a time — and what it buys is the absence of a deadlock. A process holding both `faiss-cpu` and `torch` on macOS holds two OpenMP runtimes, a known conflict with no fix available to a caller ([faiss-wheels#40](https://github.com/kyamagu/faiss-wheels/issues/40), [pytorch#149201](https://github.com/pytorch/pytorch/issues/149201)), and the suite hung there reproducibly: main thread inside `swigfaiss.search`, beside an OpenMP worker with no Python frame. The documented workaround for the conflict, `KMP_DUPLICATE_LIB_OK=TRUE`, is described by its own authors as liable to silently produce incorrect results, which is not a trade this project makes for a green build.
